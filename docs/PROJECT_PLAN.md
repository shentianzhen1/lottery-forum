# 彩票论坛｜产品与开发路线规划 V0.3

> 状态：规划基线，M0 审计阶段。本文中的技术选型和功能均为计划，除非代码与测试证明，否则不得标记为已实现。
> 产品核心约束：**主要页面以横屏为第一设计方向**。

## 1. 产品定位

「彩票论坛」是一个可扩展的多玩法基础平台。第一阶段优先建设跨平台客户端、服务端基础能力、玩法扩展接口、可追溯积分账本及后台管理框架；先交付 Android 测试版本，并为未来 iOS 适配保留空间。

产品名称固定为「彩票论坛」。用户界面统一使用「版主」「开通版主」「版主中心」等术语；开通为达标自助，无需人工审核。

积分定义、产品说明与实际功能必须一致。不得仅通过替换敏感词掩盖实际业务性质。当前范围不实现现金充值、提现、兑付或用户间积分转账/收款；涉及真实价值或受监管业务的扩展必须先进行适用的法律与合规评估。

## 2. 产品模块

### 用户端
- **首页**：热门玩法、玩法分类、公告/活动信息、个人积分入口。
- **玩法中心**：统一展示已启用的玩法插件。
- **玩法详情**：按玩法类型加载输入组件、规则说明和结果展示。
- **积分中心**：余额与可追溯的积分变动明细。
- **版主中心**：达标开通、开通状态、权限与配置、操作记录。
- **个人中心**：账户资料、安全设置、历史记录。

### 管理后台
- 用户和角色权限管理。
- 玩法插件注册、配置、版本和启停管理。
- 版主门槛与权限管理（无需人工审核）。
- 积分账目查询和受控异常处理。
- 系统配置、操作审计、错误日志与运行状态。

### 暂不纳入范围
- 聊天、好友、私信、社区动态。
- 用户之间的积分转账或收款。
- 现金充值、提现、兑付。
- 未经合规评估的真实价值交易及相关业务流程。

## 3. 核心设计约束：横屏优先

### 3.1 布局原则
- 主要页面以横屏作为第一设计和验收方向，不是把竖屏页面拉宽或只强制旋转设备。
- 首要参考画布为 16:9 横屏，并兼顾 16:10、不同分辨率和安全区域。
- 优先利用横向空间：顶部/侧边导航、分栏、多列卡片、左右信息面板。
- 避免内容拉伸、大片空白、弹窗裁切、操作区拥挤、文字溢出和过度纵向滚动。
- 组件使用弹性布局和约束布局，不以单一设备的固定像素作为全局基准。

### 3.2 页面布局建议
- **首页**：左侧导航或分类，中间热门玩法，右侧/顶部用户积分与公告。版主中心是独立入口，不取代首页主体。
- **玩法页**：左右分栏或多面板；输入/配置区与主要内容区分离。
- **积分页**：余额摘要与明细列表并列展示，保证账目可读。
- **版主页**：开通状态、权限说明、配置与操作记录清晰分区。
- **后台**：优先采用适合横屏的侧边导航、表格与详情面板组合。

### 3.3 方向与跨平台
- 横屏是默认设计与测试方向；竖屏如需支持，应通过响应式布局适配。
- 不要未经评估就在全局无条件锁定方向。检查 Flutter 方向配置、路由切换、系统栏、安全区域、键盘和弹窗行为。
- 避免不必要的 Android 专有依赖，为 iOS 保持合理的跨平台布局。
- 每个主要页面必须通过横屏验收后才能标记完成。

### 3.4 横屏验收矩阵
至少验证：
- 16:9 手机横屏。
- 16:10 或相近比例的平板横屏。
- 不同分辨率和系统安全区域。
- 首屏内容完整性、主要操作可达性。
- 键盘、弹窗、系统栏、页面切换及方向变化后的状态保留。
- 无关键文字溢出、按钮遮挡、内容裁切或异常空白。

## 4. 技术基线（待 M0 审计确认）
- 客户端：Flutter。
- 后端：Python FastAPI，模块化单体优先。
- 数据库：PostgreSQL。
- Redis：仅在缓存、限流或任务需求明确时引入。
- 本地开发：Docker Compose。
- CI：GitHub Actions。
- 首期交付：Android 横屏测试包、部署/运行说明和测试报告。

先审计现有仓库，再确定具体技术选型。不得未经评估推倒重建。玩法规则与平台公共能力分离；用户、权限、积分账本、审计、配置和插件接口应作为可复用基础能力。

## 5. 关键数据与系统边界
- **用户/角色**：认证身份、角色、状态、授权范围。
- **玩法插件**：唯一标识、名称、类型、版本、参数模式、状态、兼容性。
- **积分账户/账本**：余额投影、变动方向、数量、原因、关联业务、幂等键、创建时间、操作者与审计信息。
- **版主开通/授权**：开通状态、冻结门槛、授权范围、变更历史（无审核人/审核意见）。
- **审计事件**：操作者、动作、目标对象、结果、时间及必要上下文。

积分变动必须可追溯；避免直接无记录地修改余额。需要考虑事务一致性、并发更新、重复请求防护、权限隔离和受控纠错流程。具体模型须在 M1 设计评审后确定。

## 6. 开发路线图

### M0｜仓库审计与需求冻结
- 检查 README、开发规范、目录、分支、提交、未完成任务、依赖和 CI。
- 将实际实现与规划逐项对照。
- 确认产品边界、术语、权限和积分规则。
- 把横屏要求纳入设计与验收规范。
- 产出差距清单、风险清单和下一步任务。

**完成标准：** 有基于仓库证据的现状报告、优先级清单、明确验收条件；没有把计划写成已完成。

### M1｜基础工程与账户
- 建立/完善 Flutter 与 FastAPI 工程、数据库迁移和配置管理。
- 实现基础鉴权、用户角色和统一错误处理。
- 设计积分账本与审计模型。
- 建立横屏应用骨架、导航和响应式基础组件。
- 建立单元测试、API 测试与 CI。

**完成标准：** 可重复运行的开发环境、基础 API 和数据库迁移通过测试；核心页面骨架在目标横屏比例下正常显示。

### M2｜玩法插件框架
- 定义玩法注册、输入校验、配置版本、启停状态和统一接口。
- 用模拟数据验证至少两种不同结构的示例玩法。
- 将玩法规则与平台公共模块解耦。
- 建立插件规则测试和通用横屏页面骨架。

**完成标准：** 新增示例玩法不需要复制平台核心业务；参数校验和测试可重复运行。

### M3｜用户端与后台
- 完成横屏首页、玩法中心/详情、积分中心、版主中心、个人中心。
- 完成后台用户、插件、权限、积分查询和审计功能。
- 定义并测试前后端 API 契约与错误码。
- 为主要页面建立横屏回归测试清单。

**完成标准：** 关键用户流程可端到端演示，权限验证有效，主要页面通过横屏验收。

### M4｜安全与质量
- 测试越权访问、重复请求、并发账目更新和异常回滚。
- 验证积分账本一致性与审计完整性。
- 检查密钥、日志、依赖和接口安全。
- 运行完整测试与 CI，并修复阻断问题。

**完成标准：** 无已知的阻断级测试失败；风险和未解决问题均有明确记录。

### M5｜测试版交付
- 生成 Android 横屏测试包。
- 提供安装、配置、运行、排障文档。
- 输出测试报告、已知问题及后续任务。
- 验证跨平台架构没有不必要的 Android 专属耦合。

**完成标准：** 新环境可按文档复现构建和运行，核心横屏流程通过验收。

## 7. 开发协作规则
1. GitHub 仓库是项目状态的主要依据；所有状态结论都应与当前代码、提交或测试结果对应。
2. 开发前检查项目规范、README、TODO、当前分支、最新提交、CI 和未完成任务。
3. 不擅自重写已有实现，不擅自合并 PR、删除分支或执行不可逆操作。
4. 每次聚焦一个可验证目标，明确修改文件、测试方法和验收标准。
5. 未运行的测试不得报告为通过；未实现的功能不得标记完成。
6. 未确认事项登记为待决策项；不阻塞独立基础框架任务。
7. 主要页面的横屏适配是正式验收项，不是可选的视觉优化。
8. 产品文案与实际功能必须一致；涉及真实价值或受监管业务的扩展先进行合规评估。

## 8. M0 首轮审计报告格式
1. 仓库与技术栈现状。
2. 目录结构、分支、最新提交、CI 状态。
3. 客户端、后端、数据库、插件、积分账本、版主中心、后台的实际完成度。
4. 横屏现状及需改造页面。
5. 阻塞项、重要风险、可延后事项。
6. 基于真实代码调整后的 M0—M5 任务。
7. 下一项最有价值且依赖已满足的任务。
8. 修改文件、测试命令、横屏验证矩阵和通过条件。

如果缺少仓库访问或执行环境，必须明确说明，不得假装已完成修改或测试。
