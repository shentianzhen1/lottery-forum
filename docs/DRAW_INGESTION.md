# 开奖数据采集边界

当前阶段只建立**开奖观察（draw observation）证据层**，目标是先把外部或人工获得的开奖内容安全、可追溯地保存下来。

## 当前已实现

管理员接口：

- `POST /api/v1/draws/observations`
- `GET /api/v1/draws/observations`

写入字段：

- `provider`：来源标识
- `lottery_id`：彩种
- `raw_code`：来源原始期号
- `normalized_code`：本系统规范期号
- `draw_date`：开奖日期（`YYYY-MM-DD`）
- `main_numbers`：基本号码
- `extra_numbers`：附加号码；当前仅保存，不解释业务含义
- `raw_payload`：原始响应/人工录入的原始对象

系统生成：

- `content_hash`：规范化内容 SHA-256
- `fetched_at`：服务器记录时间
- `version`：同来源、同彩种、同规范期号的内容版本
- `status=PENDING_REVIEW`

## 幂等与更正规则

- 同一 `provider + lottery_id + normalized_code + content_hash` 重复提交，返回原观察记录，不重复落库。
- 同一来源、同一彩种、同一期号出现不同内容时，不覆盖旧记录；新内容写为 `version + 1`。
- 所有版本都保留，等待人工复核。当前没有“自动选择最新版本即为正确结果”的逻辑。

## 当前校验

目前只开放 `fujian-31` 观察记录：

- 基本号必须 7 个；
- 基本号必须互异；
- 基本号范围 `1..31`；
- 附加号码如存在，也必须为 `1..31` 且自身不重复。

附加号码与基本号之间的业务关系暂不硬编码；在官方规则/来源字段语义确认前，仅作为原始观察信息保存。

## 明确未实现

本模块目前**不会**：

- 自动调用任何第三方开奖 API；
- 自动把外部期号映射为本系统期号；
- 修改 `rounds` 期号状态；
- 生成 `WIN / LOSS / VOID` 判奖结果；
- 调用结算接口；
- 冻结、扣除、增加或派奖任何积分；
- 因“最新一条观察”自动覆盖历史更正版本。

后续应先完成来源授权/稳定性确认和连续多期人工对账，再单独设计“人工确认后的正式开奖结果”与判奖阶段。开奖观察层与资金结算层继续保持解耦。
